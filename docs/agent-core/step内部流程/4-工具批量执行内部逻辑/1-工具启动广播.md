# 工具启动广播 — toolStart 消息的组装

> 源码: `backend/agent/engine.py:278-289`；摘要器 `backend/agent/tools/summaries.py:15-109`

### 📋 **方法作用**

在工具执行前向前端宣告"这个工具开始跑了"：确定活动条目的 eventId、用厂商无关的输入摘要（绝不发原始参数全文）组装 toolStart 消息。

---

### 🔄 **主要逻辑流程**

#### **1️⃣ eventId 确定（第 280 行）**

```python
tool_event_id = tool_call.id or self._next_event_id("tool")
```

**✅ 常态：** 用 Provider 的 call_id——与 Phase 2 流式预告发的 toolStart 是**同一 ID**。

**❌ 回退：** ID 缺失时生成 `tool-{variant}-{hex8}`。

#### **2️⃣ 去重判定（第 281-289 行）**

```python
if tool_event_id not in started_tool_ids:
    await self._send(
        "toolStart",
        data={
            "name": tool_call.name,
            "input": summarize_tool_input(tool_call, self.file_state),
        },
        event_id=tool_event_id,
    )
```

**验证逻辑：**
- `started_tool_ids` 由 Phase 2 的 `_handle_streamed_tool_delta` 填充——流式阶段已预告过的工具**不再重发**；
- 前端因此把"流式预览条目"与"正式执行条目"归并为同一活动。

#### **3️⃣ 输入摘要（summaries.py 按工具定制）**

| 工具 | 摘要内容 | 压缩策略 |
|------|---------|---------|
| `create_file` | path + contentLength + 200 字预览 | **绝不发全文**（可能几十 KB） |
| `edit_file` | 每条 old/new 各截 160 字 + count | 批量 edits 逐条摘要 |
| `generate_images` | count + 提示词列表 | 提示词本身短，全发 |
| `extract_assets` | count + 描述列表 | 同上 |
| `edit_images` | count + 每条 prompt/urls/aspect_ratio | 全发（模型需核对） |
| `save_assets` | asset_ids 摘要 | 委托 uploaded_assets.tools |
| 其它 | 原始 args | 已足够短 |

---

### 🎯 **设计亮点**

1. **摘要即隐私边界**：前端只需"看懂在干什么"，toolStart 载荷被硬性压缩——WebSocket 消息量与 UI 渲染成本双控。
2. **ID 归并策略**：流式预告与正式执行共享 ID，AgentActivity 面板不会出现同一工具两个条目。

---

### 📊 **返回值结构**

| 字段 | 类型 | 说明 |
|------|------|------|
| 前端消息 | `{type:"toolStart", data:{name, input}, eventId, variantIndex}` | input 为摘要 dict |

---

### 💡 **典型使用场景**

- 前端 AgentActivity 出现"🔨 create_file — index.html (24.3 KB)"条目即由此驱动。

---

### 🔗 **与其他方法的协作**

```
turn.tool_calls 循环
  │
  ├── tool_call.id（Provider 提供）
  ├── started_tool_ids（Phase 2 填充）
  │
  ▼
summarize_tool_input ──→ _send("toolStart")
  │
  └── 同一 eventId 后续跟 toolResult（Phase 4-④）
```
