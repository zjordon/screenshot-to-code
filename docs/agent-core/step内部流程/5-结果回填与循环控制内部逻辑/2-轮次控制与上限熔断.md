# 轮次控制与上限熔断 — for-range 循环骨架

> 源码: `backend/agent/engine.py:218-221`（骨架）、`engine.py:327`（耗尽熔断）

### 📋 **方法作用**

Agent 循环的结构保证：用 `for _ in range(30)` 硬性框住轮数，耗尽即抛通用异常——模型打转（反复 edit_file 却不收敛）的最后防线。

---

### 🔄 **主要逻辑流程**

#### **1️⃣ 循环骨架（第 218-221 行）**

```python
async def _run_with_session(self, session: ProviderSession) -> str:
    max_steps = 30

    for _ in range(max_steps):
        # Phase 2 流式决策 → Phase 3 判定 → Phase 4 执行 → Phase 5 回填
```

**✅ for-range 而非 while：**
- 上限是结构属性而非状态维护——没有 `step += 1` 可被遗漏或绕过；
- 循环变量 `_` 弃用——引擎不依赖轮号（轮号由 recorder 的 `_step` 独立计数）。

#### **2️⃣ 三个提前出口（在循环体内 return/raise）**

| 出口 | 位置 | 语义 |
|------|------|------|
| `return _finalize_response(...)` | L264-265 | 正常完成 |
| `raise BudgetExceededError()` | L276 | 预算熔断 |
| （异常自然上抛） | 任意行 | 提供商/工具意外错误 |

#### **3️⃣ 耗尽熔断（第 327 行）**

```python
raise Exception("Agent exceeded max tool turns")
```

**验证逻辑：**
- 能走到这一行 = 30 轮全部"有工具调用且预算未超"——典型的打转模式；
- 用**通用 Exception** 而非专用类：与普通失败同待遇（`_run_variant` 通用 except 翻译为 variantError；eval runner 会重试——预算熔断才是不重试的特例）。

---

### 🎯 **设计亮点**

1. **双护栏分工**：预算熔断拦"太贵"（专用异常、不重试），轮次熔断拦"太久"（通用异常、可重试）——资源维度与时间维度各有其主。
2. **30 的隐含成本上限**：即便全用最贵模型，30 轮 × 单轮上限也构成事实兜底——两道护栏互为冗余。

---

### 📊 **返回值结构**

| 字段 | 类型 | 说明 |
|------|------|------|
| 正常出口 | `str` | 最终 HTML（经 _finalize_response） |
| 熔断出口 | `Exception` | 文案 "Agent exceeded max tool turns" |

---

### 💡 **典型使用场景**

- 复杂截图 + 高思考模型偶发打转：连续 edit_file 微调 20+ 轮后收敛在 30 轮内属常态；真正耗尽的 run 在 agent-runs 前端可见（events.jsonl 满步数无 run_end 的成功态）。

---

### 🔗 **与其他方法的协作**

```
for _ in range(30)
  ├── Phase 2 stream_turn
  ├── Phase 3 判定（出口 A/B）
  ├── Phase 4 工具执行
  └── Phase 5 回填 → 回到 Phase 2
        │
        └── 循环自然结束（无 return）
              │
              ▼
        raise Exception → run() BaseException 兜底 → record_run_end("failed")
```
